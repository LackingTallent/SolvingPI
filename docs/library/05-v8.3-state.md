## 2. The core output model

**It is a straight product — no facility cap, no min().** The only implementation:
`src/js/03-mechanics.js:139-148`:
```js
function weeklyP1PerColony(densityPct, programHours) {
  const d = Number(densityPct);
  /* No upper clamp. EVE's own scan reports above 100% — a user had a planet
     reading 105 — and silently rewriting that to 100 understates his yield
     while showing him a number he did not enter. Floor at 0 only. */
  const pct = isFinite(d) ? Math.max(0, d) : 0;
  const h = (isFinite(programHours) && programHours > 0)
    ? Math.min(programHours, PROGRAM_HOURS_MAX) : PROGRAM_HOURS_DEFAULT;
  return P1_PER_EXTRACTION_COLONY * (pct / 100) * extractionEfficiency(h);
}
```
with `P1_PER_EXTRACTION_COLONY = 53760` (`01-data.js:953`, = 1,152,000 P0/day × 7 ÷ 150) and
`extractionEfficiency(h) = p0PerDayForProgram(h) / P0_PER_DAY_BASELINE`
(`03-mechanics.js:131-133`; baseline = 6h program, `01-data.js:963`).

- **Extractor→facility coupling is implicit and linear.** Because 53,760/wk is defined as
  "what 8 saturated Basic facilities refine" and the 6h extractor supplies ≈100.7% of that
  draw (1,160,448 vs 1,152,000 P0/day), the formula is equivalent to
  `extractor P0 supply × density ÷ 150`, i.e. **facility output scales linearly with supply**.
  There is no `min(facility cap, supply/150)` anywhere.
- **Starvation (long programs):** output falls linearly with efficiency (24h → 81.5%,
  168h → 34.0%, 336h → 21.9%). No discrete idle-cycle modeling; the only place starvation is
  described honestly is the UI readout `12-extraction.js:20-28` ("Feeds only N% of 8
  facilities — they will idle"), which does not feed the plan numbers.
- **Over-capacity (density>100 and/or programs <6h):** claimed P1 **exceeds what 8 Basic
  facilities can physically produce** (8 × 20/cycle × 48 cycles/day × 7 = 53,760/wk hard
  ceiling). At density 105 and a 1h program (eff ≈ 1.07) the model claims ≈ 60,4xx P1/wk from
  a colony whose facilities top out at 53,760. Nothing caps it — and v8.3 *asserts* the
  uncapped behaviour as correct (`tools/test-matrix.js:324-328`, `tools/test-engine.js:24-25,32-33`).
  The refining colony (new, §7) makes the implied assumption explicit: it produces exactly
  `P1_PER_EXTRACTION_COLONY` because "the facilities are identical and are fed to capacity"
  (`05-allocator.js:333-335`) — i.e. 53,760 *is* the facility ceiling, which the extraction
  formula is allowed to exceed.
- The judge cannot catch this: it computes production from the same function
  (`04-world.js:202-204` `flow(p1).produced += weeklyP1PerColony(dens, programHours) * (l.ecus / k);`).

## 3. Colony archetypes

- **Hardcoded**, single source `src/js/01-data.js:951-958`: `STORAGE_M3 = 12000`,
  `CYCLES_PER_WEEK = 24*7`, `P1_PER_EXTRACTION_COLONY = 53760`,
  `ADV_FACILITIES_PER_COLONY = 24` ("CCU5: 2 factories x 12 Advanced"),
  `HITECH_FACILITIES_PER_COLONY = 16`, `P2_OUT_PER_ADV = 840`, `P3_OUT_PER_ADV = 504`,
  `P4_OUT_PER_HITECH = 168`; plus `BASIC_FACILITIES_PER_COLONY = 8` (`03-mechanics.js:53`)
  and `LAUNCHPAD_M3 = 10000` (`03-mechanics.js:77`). The quota calculator alone exposes
  `advFactories`/`hiTechFactories` as caller parameters (defaults 24/16, `28-quota.js:87-88`).
- **No CPU/powergrid model anywhere** (grep confirms; the only "CPU" hits are the commodity
  "Water-Cooled CPU"). CC levels below V are not modelled. Our independent CPU/PG check
  (ECU+10 heads+8 basic+pad fits at 81% PG; 24-adv+pad+storage at 97%; 25 adv fits, 26 not;
  19 HT fits, 20 not) confirms 8/24/16 are **community conventions, not maxima** — the code
  treats them as physics.
- **Storage/launchpad reasoning** exists only in (i) the lazy/QOL storage-overflow check
  (`09-modes.js:296-308`: `m3PerInterval <= LAUNCHPAD_M3`, "launchpad fills in ~N hours")
  and (ii) the extraction-panel readout (`12-extraction.js:19-28`). No multi-launchpad
  reasoning anywhere; the allocator's colonies have no storage constraint at all.
- **"Extractor slice" (k)**: k ∈ 1..5 is fixed per plan (`maxUnits` sweeps all five,
  `05-allocator.js:560-567`; `MAX_RESOURCES_PER_COLONY = 5`, `01-data.js:964`). A colony's 8
  Basic facilities are split evenly across k ECU lines, so one slice = 1/k of the colony's
  P1 capacity for one P0: `const perSlice = cand.weeklyP1 / k;` (:280). Slices are taken
  fractionally per planet (`fracUsed`, :281-292), then charged as whole colonies
  (`Math.ceil(fracUsed − ε)`, :299) and dealt into colonies ≤k slices each (:305-313); several
  slices may share one resource (the "Ionic Solutions ×5" case the measurement oracle got
  wrong twice — `docs/FINDINGS.md`). The judge's R4 mirrors it: k = Σ ecus ≤ 5, yield per
  line = `weeklyP1PerColony(dens, h) × ecus/k` (`04-world.js:186-204`). Conservative bias:
  emitted colonies may slightly out-produce the accounting, never under (:24-27).

## 4. Decay implementation

Unchanged from the snapshot (files identical):
- `extractorTotalOutput` (`03-mechanics.js:98-115`) — CCP's published formula, midpoint-
  sampled per cycle: `t = (cycle+0.5) × barWidth`, `barWidth = PI_SUB_CYCLE_SEC/900`,
  decay `qty/(1 + t×0.012)`, noise `max((cosA+cosB+cosC)/3, 0) × 0.8`, phaseShift `qty^0.7`.
- **Still hardcoded 30-minute sub-cycles for all program lengths**: `PI_SUB_CYCLE_SEC = 1800`
  (`01-data.js:962`), `totalCycles = round(hours×3600/1800)`. Game-correct cycle-time steps
  (15min ≤25h, 1h ≤50h, 2h ≤100h, 4h >100h) are not modelled — independently verified to move
  totals ≤1.1%, so low-impact but still a knowing simplification.
- **Still `PI_QTY_PER_CYCLE_BASE = 13277.2694`** (`01-data.js:961`, "exact-solved; integer
  13277 was 0.05% low") — calibrated so `extractorTotalOutput(6) === 290112`, asserted by the
  gate (`tools/verify.js:518-538`, executes the function and requires 290,112) and
  `test-engine.js:19-20`.
- **No per-cycle integer truncation**: the loop accumulates floats; the game shows integer
  per-cycle quantities. Total-level rounding only (display concern).
- **Density definition relative to the base**: density does NOT scale `qtyPerCycle` into the
  decay formula. The decay model runs once at the calibrated base (= the 290,112 "Miner-00"
  template configuration ≡ 100%), producing `extractionEfficiency(h)`; density multiplies the
  *output* linearly in `weeklyP1PerColony` (§2). So "100% density" is defined as "whatever
  head/skill configuration the community template's 290,112 corresponds to", and the
  qty^0.7 phase term is never evaluated at any other quantity.
- Doc figures 81.5% / 34.0% / 21.9% (`docs/FORMULAS.md:50-52`) are asserted against the
  engine in `tools/test-ui.js:323-325`. (Independently verified exact.)

## 8. New suspicious items in v8.3 (not in the old list)

1. **Product-mode and QOL result cards hardcode their cost lines to zero** —
   `src/js/27-engine-adapter.js:510` (`rankProductV8` success branch):
   `customsTaxAmt:0, shipping:0, salesTaxAmt:0, otherTaxAmt:0,` and no `totalM3`, while
   `gross`/`net` on the same row come from `computeEconomics` with real costs; same at :879
   (`rankQolV8`). The results tooltip prints exactly these fields
   (`17-sourcing.js:767`: "− Customs … − Shipping … − Sales tax …"), so in Product and QOL
   modes the hover breakdown shows all-zero deductions beside a net that visibly differs from
   gross — **precisely the bug that was fixed for Profit mode** (profit maps `r.customsISK`
   etc. at `27-engine-adapter.js:288-296`). The "× m³/unit = 0 m³" self-contradiction returns
   too (`totalM3` absent).
2. **The main QOL path ignores sourcing** — `lazyPlan` (`09-modes.js:256`) takes only
   `{ intervalHours, market, costs, sellSpec }` and computes every line from ground density
   (:269-271). The sourcing fix landed only in `lazyP2Throughput`, which serves the display
   panel and the `rankLazy` fallback (`17-sourcing.js:371-372`) — a fallback that in turn
   ignores the interval (:657-659). So QOL honours sourcing only when the primary path
   produces nothing and the fallback runs; at non-zero density with buyall, QOL yields are
   density-limited numbers for a user who is buying inputs. The matrix passes because 0%
   +buyall happens to fall through to the fallback. The `engineOpts` build check cannot see
   this: `lazyPlan` is not in its function list.
3. **Refining-colony ore is priced at the Jita buy side** — the new route's entire cost is
   the ore purchase (`purchases[p0] += perUnit × units × 150`, `05-allocator.js:408-412`),
   priced via the same `{buy: price, sell: price}` snapshot (§1d), so the strategy the tool
   explicitly warns is "usually the more expensive route" (`10-plan.js:102-128`) is
   systematically **flattered** by understated ore prices.
4. **Refining output has no efficiency/tier nuance** — a refining colony always makes exactly
   53,760 P1/wk regardless of `programHours` (`05-allocator.js:335`), reasonable (no
   extractor) but it means refine-vs-extract comparisons shift with the program slider for
   only one side; and only P1s are refinable (by design, but the picker offers 'refine' for
   every input).
5. **Quota whole-plan utilisation mixes units** — `28-quota.js:187-192` sums `perWeek` and
   `capacity` across extraction (P1 units) and factory lines (P2/P3/P4 units) as if
   commensurable; the headline "Spare capacity N%" is a unit-mixed figure.
6. **Quota UI defaults quietly differ from the engine defaults** — `readQuotaInputs`
   (`28-quota.js:255-266`) seeds days 30 / programHours 24, while `quotaPlan` documents
   defaults 7 / 6; combined with §1b the quota headline is doubly skewed for P3-bearing
   chains.
7. **Stale comment contradicting code**: `03-mechanics.js:135` "Density clamps 0-100 HERE"
   above code that deliberately does not clamp the top (:141-144). Harmless today; a trap for
   a future "fix".
8. **`SPACE_PRESETS` is now provably dead** (only occurrence is its declaration,
   `06-economics.js:44`) yet still ships in the bundle as a second, contradicting "typical
   costs" table — one grep away from being wired in by mistake.
